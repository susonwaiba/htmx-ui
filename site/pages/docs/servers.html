A built htmx-ui site is just files: pages at their routes, hashed scripts and styles, whatever you put in public/. Nothing about it needs a particular server. htmx-ui-engine ships adapters that mount those files on Elysia (the one to start with), Express and Hono, plus createSite() for anything else — so your backend can own /api and the pages, or the other way round, in one process.

Static or dynamic?

A page in pages/ is rendered once, by htmx-ui build, and served as a file from dist/. That is what a page route is: the same bytes for everyone, cacheable anywhere, no server involved. So anything that depends on who is asking does not belong in the built page — it belongs in a fragment your server renders per request.

That is the whole division: pages are static and come from the build; the per-user part is a site.fragment() answering an htmx request.

When the HTML depends on who is asking

A template decides what to show from its context, and at build time there is no request, so no user. Here is the piece that usually needs it — a sign-in link for a visitor, a name and a sign-out button for a member:

{% call code("jinja", title="partials/user-menu.html") %} {% raw %}{% if user %} {{ user.name }}
{% else %} Sign in {% endif %}{% endraw %} {% endcall %}

The page keeps its place in the layout and asks for that fragment; your server renders it against the request and htmx swaps it in:

{% call code("html", title="pages/dashboard.html") %} {% raw %}
…
{% endraw %} {% endcall %} {% call code("ts", title="server.ts") %} const html = (body: string) => new Response(body, { headers: { "Content-Type": "text/html; charset=utf-8" } }); app.get("/api/user-menu", ({ request }) => html(site.fragment("partials/user-menu.html", { user: currentUser(request) })), ); {% endcall %}

The page stays a static file anyone can cache, the fragment is small, and the markup lives in one template either way. This is the shape for a header, a nav, a sidebar, or any list of the visitor's own rows.

{% call alert("Only the render needs the user", variant="info") %} Your routes and the framework's own middleware see the request first, so currentUser() can be a cookie, a session or a token — anything you already have. Templates get it as a context value, never by reading the request themselves. {% endcall %}

Not sure which branch answered a request, or why a page never finishes loading? Set debug in htmx-ui.config.ts and the engine logs every request in, what answered it and how long each render took — see Debugging.

What the adapters do

htmx-ui build renders every page and writes the site to dist/. An adapter is a thin layer over that output:

  1. The config's routes answer hx-get and hx-post (see Mock htmx endpoints).
  2. dist/ answers everything else: a page at its route, an asset, a public/ file, then your built 404.html.
  3. Anything still unmatched is yours: the adapter passes the request on.
{{ code_tabs([ { id: "elysia", label: "Elysia", lang: "ts", source: 'import { Elysia } from "elysia"; import { htmxUi } from "htmx-ui-engine/elysia"; new Elysia() .get("/api/ping", () => ({ ok: true })) .use(htmxUi()) // everything else is the built site .listen(3000);' }, { id: "express", label: "Express", lang: "ts", source: 'import express from "express"; import { htmxUi } from "htmx-ui-engine/express"; const app = express(); app.get("/api/ping", (req, res) => res.json({ ok: true })); app.use(htmxUi()); // last: everything else is the built site app.listen(3000);' }, { id: "hono", label: "Hono", lang: "ts", source: 'import { Hono } from "hono"; import { htmxUi } from "htmx-ui-engine/hono"; const app = new Hono(); app.get("/api/ping", (c) => c.json({ ok: true })); app.use(htmxUi()); // last: everything else is the built site' } ]) }} {% call alert("Mount it last", variant="info") %} Every adapter is a fallback: register your own routes and middleware before it, so they keep the paths they want and htmx-ui answers the rest. Elysia is the exception — a specific route always beats the plugin's catch-all, so order doesn't matter there. {% endcall %}

Add the adapter to the project next to the pages, alongside htmx-ui itself:

{{ cli("add htmx-ui htmx.org\nadd-dev htmx-ui-engine tailwindcss\nadd elysia") }}

Adapters import nothing from their framework, so they only add types and runtime methods — never a second copy of Express, Elysia or Hono, and nothing to install for the ones you don't use.

Scripts

{% call code("json", title="package.json") %} { "scripts": { "dev": "htmx-ui dev", "build": "htmx-ui build", "start": "node server.js" } } {% endcall %}

Templates are rendered when you build, so run htmx-ui build before starting your server. While you work on pages, htmx-ui dev is the faster loop: hot reload for scripts and styles, a reload when a layout, partial, macro or data file changes, and the mock endpoints from your config to build against.

createSite()

The adapters are thin, so anything they do is available directly — and it is what you reach for when your server isn't one of the three, or when you want to render a page or a fragment yourself.

Resolves once, at startup."], ["site.config", "The resolved config: roots, outDir, origin, and your globals and filters."], ["site.pages", "Every page, with its file and route, sorted by route. When you render at request time, asset() returns /app.ts-style URLs by default — what a server that bundles its own assets wants. Point it somewhere else with options.asset if yours are hashed in dist/assets/. {% endcall %}

Fragments with htmx

htmx swaps HTML, not JSON, so your API returns fragments. Put them in templates next to your pages and render them with site.fragment(): same macros, same components, same asset(), and no duplicated markup.

{% call code("jinja", title="partials/invoice-row.html") %} {% raw %} {{ invoice.number }} {{ invoice.total }} {% endraw %} {% endcall %} {% call code("ts", title="server.ts") %} import { Elysia } from "elysia"; import { createSite } from "htmx-ui-engine"; import { htmxUi } from "htmx-ui-engine/elysia"; const app = new Elysia(); const site = await createSite(); app.get("/api/invoices/:id/refund", ({ params }) => { refund(params.id); return site.fragment("partials/invoice-row.html", { invoice: invoices.get(params.id) }); }); app.use(htmxUi({ site })); // the same site, so templates stay in one place app.listen(3000); {% endcall %}

Any template works, not just partials: a page shell, a component wrapper, a whole page you want to push into a modal. Return it with the content type htmx expects:

{% call code("ts", title="A fragment as a Response") %} const html = site.fragment("partials/invoice-row.html", { invoice }); return new Response(html, { headers: { "Content-Type": "text/html; charset=utf-8" } }); {% endcall %}

Render a page per request

To build a page from request data — a user's name, a filtered list — render it yourself and send it. The result is still the built page for that route, with your context merged in. See when the HTML depends on who is asking for when this is the right shape and when a fragment is enough.

{% call code("ts", title="server.ts") %} app.get("/", ({ request }) => site.render("/", { user: currentUser(request) })); {% endcall %}

Put the values in the page's context, not in a global, and remember that transform() from your config still runs (heading anchors, and so on) — it is the same renderer the build uses.

Deploying

An adapter serves static files, so the deployment is your server's: build during the release, then run it. Which routes your server has to answer is the only real choice, and there are three shapes.

1. Static only

htmx-ui build, then ship dist/ to a static host, a CDN or an object store. No server, no config to change. This needs the pages themselves to be the same for everyone — the config's routes and fetch are not in the build, as Mock htmx endpoints explains, so anything htmx asks for has to be another host.

{% call code("bash", title="Terminal") %} htmx-ui build {% endcall %}

2. Static pages, dynamic fragments

The usual shape. Page routes are always static — they are built and served from dist/ — and the per-user part is a fragment rendered per request, so it arrives as a request instead of being baked into the HTML. That means your server needs the Nunjucks templates, which htmx-ui build does not copy: it writes built pages and hashed assets, and nothing else.

Ship the source tree next to dist/ and there is nothing to configure — the defaults already point at pages/ and the project root. To ship less, copy the templates you render from into the deployment and repoint the config:

{% call code("bash", title="Terminal") %} htmx-ui build mkdir -p dist/_templates cp -r layouts partials pages dist/_templates/ cp -r data dist/_templates/ {% endcall %}

Copy whichever of these you have — macros/ and components/ too if your templates import from them — and everything a template reaches at render time, which is what json() and svg() read.

{% call code("ts", title="htmx-ui.config.ts") %} import { defineConfig } from "htmx-ui-engine"; export default defineConfig({ // This deployment renders templates at runtime: check at startup that they arrived. render: true, // Where the copy landed: "." stays the project root, the copy is searched second. roots: [".", "dist/_templates"], pages: "dist/_templates/pages", }); {% endcall %} {% call code("ts", title="server.ts") %} const site = await createSite(); // reads the config above, from the deployment directory new Elysia().use(htmxUi({ site })).listen(3000); {% endcall %}

render is what turns a packaging mistake into a failed start rather than a 500 later: with it on, createSite() checks the template roots and the pages directory at startup and tells you what to copy if they are missing. Without it a deployment that forgot its templates starts happily, finds no pages, and only fails on the first htmx request.

{% call alert("asset() in a fragment", variant="warning") %} A fragment usually needs no URLs — svg() and the icon() macro inline their markup, so there is no file to fetch. When one does need a project image, asset() returns a path from the project root, which your server only serves if that file is under dist/. Either link to the built asset directly, or map the files yourself with options.asset. {% endcall %}

3. Everything from your server

Nothing is served as a static file: your server answers each route, rendering the page or a fragment for it, with data that is never the same twice. Same shape as above — ship the templates, set render — with the addition that you register the routes instead of relying on dist/:

{% call code("ts", title="server.ts") %} app.get("/dashboard", ({ request }) => html(site.render("/dashboard", { user: currentUser(request) }))); app.get("/api/team", ({ params }) => html(site.fragment("partials/team.html", { team: teams.get(params.id) }))); {% endcall %}

You are now responsible for caching: hashed assets in dist/assets/ can still be cached forever, but a page rendered per request is yours to send Cache-Control for, per visitor.

Cache headers

The adapters set content types and nothing else, so your server adds cache headers and compression. The usual split: hashed assets in dist/assets/ forever, HTML not at all.
